# ДЗ №3 — HTTP і HTTPS без модулів `http`/`https`

HTTP-сервер, написаний поверх сирого TCP (`net.createServer`), і той самий обробник,
піднятий поверх TLS (`tls.createServer`). Модулі `http` і `https` не використовуються
свідомо: мета — побачити, що HTTP це просто текстовий протокол над потоком байтів, а
HTTPS — той самий протокол над зашифрованим потоком, а не окрема технологія.

Сторонніх npm-залежностей немає. З рантайму — тільки `net`, `tls`, `fs`.

---

## Структура

```
src/
  handler.ts        спільний обробник з'єднання: кадрування → парсер → роутер → серіалізатор
  server.ts         транспорт HTTP  — net.createServer(handleConnection).listen(3000)
  https-server.ts   транспорт HTTPS — tls.createServer({key, cert}, handleConnection).listen(3443)
  status.ts         таблиця статус-кодів і reason-фраз
scripts/
  setup-certs.sh    генерація самопідписаного серта
  verify-ac.sh      прогін критеріїв приймання
test/
  http.test.mjs     чорноскриньові тести HTTP
  tls.test.mjs      те саме по TLS + перевірка, що обробник справді той самий
certs/              згенеровані ключі — у .gitignore, не комітяться
```

Джерело правди й рантайм — `.ts` напряму: Node ≥22 стрипає типи на льоту, тому
окремого build-кроку (`tsc`) немає — `npm start` і критерії приймання (grep на
`net.createServer` / `tls.createServer`) працюють просто зі `src/*.ts`.

---

## Запуск

```bash
npm install
npm run certs        # згенерувати самопідписаний серт у certs/
npm start            # HTTP  на http://localhost:3000
npm run start:https  # HTTPS на https://localhost:3443
```

Порт перевизначається через `PORT`, напр. `PORT=8080 npm start`.

Маршрути:

| Маршрут    | Відповідь                                            |
|------------|------------------------------------------------------|
| `/`        | 200, коротке текстове привітання                      |
| `/headers` | 200, заголовки запиту, розпарсені в мапу, ключі в lower-case |
| решта      | 404                                                   |

Перевірка:

```bash
curl -sv http://localhost:3000/
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/nope     # 404
curl -s http://localhost:3000/headers -H "X-Demo: abc"
curl -sk -o /dev/null -w "%{http_code}\n" https://localhost:3443/       # 200
```

`-k` у `curl` обов'язковий: сертифікат самопідписаний, тому будь-який клієнт із
дефолтними налаштуваннями відмовиться йому довіряти. Це не помилка конфігурації —
див. розбір нижче.

## Тести

```bash
npm test        # ганяє обидва набори напряму проти src/*.ts
```

Тести чорноскриньові: піднімають сервер окремим процесом на вільному порту й
розмовляють із ним сирими байтами. Останній тест `tls.test.mjs` порівнює тіло
відповіді `GET /` по TCP і по TLS побайтово — це машинна перевірка того, що
обробник справді один, а не скопійований у два файли.

Перед здачею:

```bash
npm run verify  # прогін усіх критеріїв приймання з умови ДЗ
```

## Генерація сертифіката

Скрипт `npm run certs` виконує саме це:

```bash
openssl req -x509 -newkey rsa:2048 -nodes \
  -keyout certs/localhost-key.pem \
  -out    certs/localhost-cert.pem \
  -days 365 \
  -subj "/CN=localhost" \
  -addext "subjectAltName=DNS:localhost,IP:127.0.0.1"
```

Що означають прапорці:

| Прапорець | Навіщо |
|-----------|--------|
| `-x509` | одразу видати готовий сертифікат, а не CSR на підпис комусь |
| `-newkey rsa:2048` | згенерувати нову пару ключів RSA-2048 разом із сертифікатом |
| `-nodes` | «no DES» — не шифрувати приватний ключ парольною фразою, інакше сервер питав би пароль на кожному старті |
| `-subj "/CN=localhost"` | не питати поля інтерактивно |
| `-addext subjectAltName=...` | сучасні клієнти звіряють ім'я хоста з SAN, а `CN` ігнорують; без SAN помилка буде не про самопідпис, а про невідповідність імені |

Ключі й сертифікати в `.gitignore` і в репозиторій не потрапляють — приватний ключ у
git це компрометація назавжди, бо історію переписати вже не вийде.

## Debug-сесія: `openssl s_client`

Піднімаємо HTTPS-сервер і дивимось на рукостискання очима клієнта:

```bash
npm run start:https
openssl s_client -connect localhost:3443 -servername localhost </dev/null
```

`</dev/null` тут не косметика: без нього `s_client` після рукостискання перейде в
інтерактивний режим і чекатиме, поки ти щось надрукуєш. `-servername localhost`
вмикає SNI — розширення, яким клієнт повідомляє бажане ім'я хоста ще до того, як
сервер обере сертифікат.

```
depth=0 CN=localhost
verify error:num=18:self-signed certificate
verify return:1
depth=0 CN=localhost
verify return:1
CONNECTED(00000005)
---
Certificate chain
 0 s:CN=localhost
   i:CN=localhost
   a:PKEY: rsaEncryption, 2048 (bit); sigalg: RSA-SHA256
   v:NotBefore: Aug  8 08:39:48 2026 GMT; NotAfter: Aug  8 08:39:48 2027 GMT
```

`verify error:num=18:self-signed certificate` — очікувана реакція клієнта: у сертифіката
немає підпису довіреного CA, тож OpenSSL відмовляється підтвердити особу сервера, хоча
саме TLS-рукостискання все одно завершується успішно й трафік шифрується.

### Коди перевірки ланцюжка

| Код | Значення | Коли трапляється |
|-----|----------|------------------|
| 18 | самопідписаний сертифікат | сертифікат підписав сам себе — ланцюжка до жодного довіреного кореня не існує; штатна ситуація для локальної розробки |
| 19 | ланцюжок неповний | корінь ланцюжка не знайдено в сховищі довіри — типово коли сервер не віддав проміжний сертифікат |
| 10 | сертифікат протермінований | поточна дата поза інтервалом `notBefore … notAfter` |

Скарга на перевірку у виводі `s_client` — це не поламаний сервер, а нормальна реакція
клієнта, у якого немає підстав довіряти цьому сертифікату: рукостискання при цьому
проходить і трафік шифрується, не підтверджена лише особистість сервера. У проді
сертифікат підписує CA, якому клієнт довіряє з коробки, і код стає `0 (ok)`.
